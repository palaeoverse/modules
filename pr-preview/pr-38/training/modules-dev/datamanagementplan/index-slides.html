What is a DMP?

  • Document presenting how data will be managed during and after a research project

  • Contains details on, for example,:

    • the project in general

    • what types of data will be created and how

    • how will data be documented

    • how data will be stored, including for how long and back-ups

    • whether there are any relevant ethical issues to consider

A DMP is a document that presents how data will be created, managed, and stored during and after a research project. It should therefore contain details on:

  • the project in general (e.g., any funding, relevant parties, a summary of the work, etc.)

  • what types of data will be created and how, such as spreadsheets, photographs, whether existing data will be reused, etc.

  • how will data be documented, including metadata

  • how data will be stored, including where, for how long, and whether it will be backed up

  • whether there are any relevant ethical issues to consider, such as personal or sensitive data

Why make a DMP?

  1. It can help you organise a big project

  2. Prevent data loss, ease sharing of data, support community best practices

  3. Many funders require one

DMPs are most importantly to help you organise large or complex projects. They give you the opportunity to think through what data you will need, the format it will take, and how you will store it in advance of actually doing the work. They give you a document that you can refer back to at any time. Overall, this can help you prevent data loss, and help you share data (both with others and your future self!). Additionally, many funders of large projects (e.g., the ERC) require you to submit a DMP, either when you apply to the grant or soon after being awarded one.

Components of a DMP

We will briefly go through a few essential components of a DMP. These are loosely organised into sections on data collection, documentation, storage, and ethical concerns, though the actual headings and structure you use is up to you (or funder, if they require a specific template to be used) and can depend on the project.

Data collection

  • File formats

  • Descriptions

  • Estimates of volume and times

  • Is it reused or generated new?

For each type of data you will collect and/or use during your project, you should briefly include:

  • the possible file formats

  • a short description of the data

  • estimates of data volumes and when the data will be collected during the project

  • whether the data will all be generated new, or whether (and where from) data will be reused

Data collection

  • How you will generate the new data

  • Where data will be reused from

For each type of data listed previously, you should then give a brief description of how you will generate the data (i.e., briefly on the methods). You should also note where you will reused data from, if needed (e.g., specific online domain-specific repositories, the published literature, etc.).

Data documentation

  • Planned file structure:

    • Predetermined hierarchical file structure

    • Visual summary that you keep up-to-date

  • Master (raw) files

    • Always keep a copy of raw data, date-stamped, unedited

  • Metadata:

    • README (see Archiving module)

    • Ensure associated protocol or required software is signposted

  • Software / code needed to access or run the data

  • Domain standards used for data creation / handling

You also need to note how your data will be documented. This might include whether you predetermine a file structure, for which you could also keep a visual summary so that you never lose anything. This is also the place to note that you will keep raw versions of created and reused data files (a good example is PBDB downloads), and how these will be stored.

You should consider what your metadata will look like, including README files (see the Archiving module) and how you will signpost to any relevant protocol or required software for reading/using the data. It is a good idea to also explicitly state any related tools/software/code that might be needed for others reusing the data you generate, and how you will share these.

Lastly, some domains have standards that can/should be used when generating certain data. You should also consider whether any of these are applicable to you, and discuss whether you will use them. For example, for palaeontological occurrence data you might choose to use the Darwin Core taxonomy (dwc.tdwg.org), and discuss that in your DMP.

Data storage

  • Repositories for storage

  • Open file formats where possible

  • Indexing and versioning

  • How long will data be preserved for?

  • What licenses will data be shared under?

There are some incredibly important decisions for you to make and detail in this section, and having a plan for this before generating data will really help you. Firstly, you should consider and detail how you will store your data. Of course, we encourage you to store data in places that it is also easy to share this data (and potentially software), such as various online repositories (e.g., Zenodo, GitHub, domain-specific repositories; see the Archiving module). As far as possible, data should be stored in these repositories in open file formats (e.g., .csv instead of .xslx), so that proprietary programmes are not needed to reuse the data. As this point, you should also consider whether the repositories you choose will allow you to easily index (e.g., through generation of DOIs) and version-control your data; we advise you to choose data storage solutions that allow this!

Secondly, you need to think about the lifespan of your data. How long will you ensure project data is preserved for? This might be for as long as online repositories allow (another point to consider in choosing a repository), or you might need to commit to a period after the project in which you keep locally stored data available on request (typically at least 10 years).

Finally, you should state in your DMP under which licenses your generated data (and software) will be shared (see Archiving module). Ideally, this would be some CC-BY license to allow maximal reuse (with attribution) for data, and software license such as GNU for code. You can also note whether you envisage any embargoes to data sharing (such as when required by journal publishers), and how you will handle these. Some repositories, such as Zenodo, allow for embargo periods.

Ethical considerations

  • Ethical issues with data collection, such as:

    • data from human subjects

    • animal studies

    • personal, confidential, or sensitive data

  • Some relevant-to-palaeontology considerations:

    • Sample collecting permits

    • Museum collection restrictions

    • Museum accessioning

    • Sensitive location data

    • Helicopter science / indigenous data

  • Data security

It is really important that you consider potential ethical, legal or security issues regarding your data collection, even though this section is likely to be shorter for most palaeontological research than for some other domains. Mostly palaeontology projects don’t need to consider data derived from human subjects, or that is personal, confidential, or sensitive, though you should confirm that this is the case. It is possible that you might be planning studies involving animals (e.g., experimental taxonomy), and this needs to be carefully discussed in your DMP. This is not the time or place to go into these potential ethical concerns, but please search out specific recommendations if you need to.

However, there are many other ethical considerations to do with palaeontological data that you should consider here, such as:

  • Will you be collecting palaeontological or geological samples? If so, you should note about permits in your DMP.

  • If the above is true, you should also include what will happen to samples after the research. Will they be accessioned in a specific museum?

  • You might be generating data from existing museum collections - if so, you should note that you will discuss sharing of this data with the curators in advance, as sometimes the museums have their own restrictions.

  • Some localities palaeontological and geological data are sourced from need to be protected, and so you might state that in these cases sensitive location data will not be shared.

  • Do you need to consider the impact of your data collection on indigenous and local communities? The DMP is a place to discuss these ethical concerns, and whether you need to take any action to address them (e.g., CARE data).

Lastly, you should briefly address data security. Usually palaeontological data pose a low security risk because there are no personal or sensitive data, though you should confirm this. Data security should also factor into your decisions about data storage locations.
